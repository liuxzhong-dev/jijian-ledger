# 计件本（jijian_ledger）

制衣厂车工的**计件工资账本**。纯离线、不联网、不要账号，一台手机自己记账自己算钱。

---

## 一、它解决的是哪个问题

车间里的计件工，每天要记：款号、扎号、码、件数、单价，还要算本款收入、加班收入、当天总收入、当月总收入。
现在多数人靠**手机备忘录手打**（就像参考的那张截图），月底对账时四行数字全靠心算——**错一次就少拿几十块**。

这个 App 只让用户填 6 个原始字段，剩下的全自动算：

| 截图里要手填的行 | 本 App 怎么处理 |
|---|---|
| 日期 | 默认今天，需要补记才改 |
| 款号 | **要填**（自动记住这个款上次的单价） |
| 扎号 + 对应码 | **要填**（扎号填了会提示"这扎今天已记 X 件"） |
| 扎号对应的件数 | **要填** |
| 单价 | **要填**（输入款号后自动带出上次单价） |
| 本款收入（单价×件数） | 自动算 |
| 加班时间 | 单独一页记，点常用时长即可 |
| 加班单价 | 自动带出上次单价 |
| 本日加班收入（时间×单价） | 自动算 |
| 总收入（款收入+加班收入） | 自动算 |
| 本月总收入 | 自动算（月账页汇总） |

**一句话：11 行变 6 行，4 处手算归零。**

## 二、做了什么 / 故意没做什么

**v1 做了**
- 记一笔：款号 / 扎号 / 码 / 件数 / 单价，实时显示这一笔多少钱
- **一颗「保存」按钮**：存好就回主页，提示里直接告诉你"已记 30 件 ¥45.00 · 今日 ¥320.00"
- **再记一扎**：主页浮标带上一扎的款号/单价/码再进来，只需填扎号和件数
- **单价记忆**：输入款号自动带出上次单价
- **扎号重复提醒**：同一扎号当天再记会提示已记件数（只提醒不拦截——一扎确实可能分两次做）
- 加班单独记账，按 0.5 小时步进，自动算钱
- 今日合计、本月合计、本月件数
- 月账：按款号汇总（件数/单价区间/金额）、按天汇总（点开看当天明细）
- 导出：**复制对账文本**（直接发微信给组长）、**复制 CSV**（粘到 Excel）
- 备份：**复制备份到剪贴板 / 从剪贴板恢复**，合并导入、自动跳过重复
- 三维外观：**背景 3 套 × 玻璃厚度 6 档 × 按钮 4 种形态**（见第八节）

**v1 故意不做**（不是漏了，是做了会拖垮 v1）
- 不做支出记账、不做分类预算——这是"挣了多少"，不是"花了多少"
- 不做云同步、账号、多设备
- 不做图表——月底对账看的是数字对不对，不是图好不好看
- 不做扫码（扫菲票需要厂里配合打码，工人单方面做不到）
- 不做多工序批量录入、不做 OCR

## 五、五个关键设计决策（改代码前先看）

| 决策 | 为什么这么做 | 换成别的会怎样 |
|---|---|---|
| **金额一律存整数「分」** | `0.1+0.2≠0.3`；1800 笔累加后差几分钱，工人就再也不信这个 App | 用 double 存钱，月底对账必现"差一分"，且找不到是哪笔 |
| **派生收入存进库**（`amount` 字段） | 月末汇总用一条 SQL `SUM(amount)` 就行，不必读几千行进内存再算；历史数据也不会因为改公式而变 | 每次现算 → 汇总慢，且改公式会让旧账跟着变 |
| **单价记忆靠"查最近一条同款号记录"** | 不建单独的价目表：少一张表就少一处要同步的真相。厂里调价时用户自己输一次新价，下次自动就是新价 | 建价目表 → 出现了"表里的价"和"记录里的价"两份数据，必然分叉 |
| **备份走剪贴板而不是文件** | 工人不会用文件管理器找路径。复制 → 粘到微信「文件传输助手」是所有人都会的动作 | 用文件导出（SAF）→ 需要选目录、找文件，多数人第一次就放弃 |
| **录入页只留一颗「保存」，保存即返回** | 原来有「保存并继续」和「记完返回」两颗，都写库、差别只在跳不跳页，名字却都像"完成"——用户猜不出区别，实际最常见的心情是"我就记一扎"。连续录入改由主页浮标「再记一扎」承担：带款号/单价/码回去，只填扎号+件数，还比留在页面上多看见一次今日合计 | 两颗按钮 → 用户记完一扎发现没别的要记，还得再点一次返回；若砍掉连续录入则老手记 5 扎要重输 5 次款号 |
| **数据库用 sqflite 而不是 Drift** | Drift 要跑 codegen（build_runner），多一层可能报错的构建步骤；这个 App 只有 3 张表，手写 SQL 完全够 | 用 Drift 前期爽，改表结构时多一步生成，出错信息也绕 |

## 五·补：衣服码数（v1.3）

v1.0 把码写死成 `S M L XL XXL 均`，主人实际用出来的 bug：**做外贸大码的厂（XXXL / 5XL / 12XL）和童装数字码（90~170）根本选不了**。

所以改成三层（`lib/core/sizes.dart`）：

| 层 | 内容 | 什么时候显示 |
|---|---|---|
| 常用 | S M L XL XXL 均码 | 默认，一屏全显示 |
| 更多 | XXXL XXXXL 5XL 6XL 8XL 10XL 12XL + 90~170 | 点「更多码」才展开 |
| 自定义 | 用户自己填，最多 8 字符，**记住最近 4 个** | 点「自定义」填，之后直接点 |

三点设计理由：

1. **不把 23 个码一次性铺开**：内销厂常用码就 6 个，铺开反而更难找，而且 `Wrap` 会占掉半屏。
2. **自定义要记住**：和「单价记忆」同一个思路——填过一次的东西，第二次就该自动带出来。记满 4 个后新的顶掉最旧的。
3. **老数据必须能兜住**：v1.0 手填的码（比如 `7XL`）不在任何列表里，编辑旧记录时也要出现在选项里并选中，否则一编辑码就丢了，账就和菲票对不上。

码只是**标签**，不参与任何计算（金额 = 件数 × 单价），所以放开写不会影响算钱。测试见 `test/sizes_test.dart`。

## 五·补二：款号速查能看明细了（v1.3）

「我的」页的款号列表原来只显示件数和金额。但对账时工人最常问的是「这个款我记了几笔、**哪一扎还没记**」——汇总回答不了。现在点款号会弹出该款的逐笔明细（日期 / 扎号 / 码 / 件数 × 单价），点任意一条直接进编辑。

对应新增 `Repo.workOfStyle(styleNo)`。

## 五·补三：菲票拍照存证（v1.4）

主人的原话：「菲票可能是手写的？而且比较长，然后比较难输入，能不能做成拍照保存的？」

菲票的实际情况是**打印手写混着来**。所以 v1.4 的目标不是「识别」，是**「免输入 + 存证」**：拍一张跟着计件记录走，对账时点开就能看清手写数字。

### 做了什么

| 位置 | 功能 |
|---|---|
| 录入页 | 扎号下面多一块「菲票」区：没拍时是通栏「拍菲票」按钮，点了弹「拍照 / 从相册选择」（相册入口是给下班前补录白天拍的票的工人留的） |
| 录入页 | 拍完显示 76×76 缩略图，点开看大图 |
| 大图页 | `ui/photo_view_page.dart`：双指缩放 0.5×~4×（拍菲票就是为了看清手写数字），**永远黑底**——全 App 唯一不随皮肤走的页面，故意的 |
| 录入页 | 换图（重新拍/选）、删图（**走确认对话框**：菲票原件拍花了，这张图就是唯一凭证，和删记录同一个安全等级） |
| 首页 / 月账 / 款号明细 | 有照片的记录，款号前面带一个小相机图标 `PhotoMark` |
| 「我的」页 | 「菲票照片」区：显示占用空间 + 「清理不再引用的照片」 |

### 照片存储的三条决策（`lib/core/photos.dart`，都来自「哪里会坏」）

1. **选完的图必须立刻转存**。image_picker 返回的文件在缓存目录里，iOS 在内存压力下会回收——不立刻 `saveTo` 到 App 自己的目录，过一会儿回来看图就是空白（安卓一般不回收，但不能赌）。
2. **只存文件名，不存绝对路径**。绝对路径在换机恢复、备份恢复后必然全部指向不存在的旧位置；文件名 + 固定目录（`getApplicationDocumentsDirectory()/feipiao`），路径永远可推导。
3. **选图时就压好**（`maxWidth 1600 / quality 85`）。原图 3~5MB，工人一天拍十几张，一个月就把手机存满；压完一张两三百 KB。参数集中在 `Photos` 类里，页面不允许自己传——否则有人忘写 quality，某天突然多出 3MB 的原图，查都不知从哪查。

外加一条安全：photo 字段的值可能来自外部导入的备份，所以取文件时过 `p.basename`——防 `../../` 之类的路径穿越读到别的文件（有测试盯着，见下）。

### 为什么不删记录时删照片，以及「清理」入口

删记录/改记录时**故意不删照片文件**——菲票原件拍花了，这张图就是唯一凭证，误触一下没了，工人得去翻垃圾桶。代价是目录里会留下孤儿文件，所以「我的」页给一个「清理不再引用的照片」入口：扫出没有任何记录引用的文件，**列清楚**（「10月21日 15:30 · 240KB」而不是 `1729500000000.jpg`，工人看不懂文件名）让用户确认再删。

### 为什么不做 OCR（调研结论，不是懒）

| 方案 | 中文手写效果 | 代价 |
|---|---|---|
| ML Kit 端侧识别 | **印刷体**优化，手写只对拉丁字母可靠 | 免费、离线，但识别不了中文手写 |
| 腾讯云通用手写体 | 官方口径 85%~92% | 0.15 元/次，要联网 + API Key，**破「纯离线」的立身之本 |
| 自训模型 | — | 单人项目不可能维护 |

所以「能识别的识别」这半句暂时搁置：**拍照免输入 + 随时放大核对**已经解决了「难输入」这个主要矛盾。等哪天有端侧中文手写方案再评估。

### 两个必须知道的边界

1. **照片不进剪贴板备份**。JSON 装不下二进制，备份只有文件名。换机恢复后记录能回来，但照片文件不在，缩略图位置显示「照片文件已丢失」——这是已知限制（第七节），不是 bug。
2. **「再记一扎」不沿用照片**。每扎的菲票不一样，沿用就是张冠李戴。

### 数据库迁移：第一次真迁移（dbVersion 1 → 2）

v1.2/v1.3 加设置项走 k/v 表，不需要迁移；v1.4 加的是列，所以 `db.dart` 的 `onUpgrade` 第一次真正干活：`ALTER TABLE work_records ADD COLUMN photo TEXT NOT NULL DEFAULT ''`。老用户的记录全部置空——他们本来就没有照片。备份 schema 同步升到 2；**老 App 读 schema 2 的备份按列名取、photo 键被自然忽略，不会炸**（有测试验证）。

测试见 `test/photo_test.dart`（7 例）：photo 存取与换图、**用真实的 v1 库 + 真实的迁移函数**验证老记录不丢且 photo 置空、备份回环（含「老 App 的无 photo 备份能导入」）、`allPhotoNames` 只收非空、**孤儿清理永远不碰被引用的照片**、路径穿越被 basename 挡住、文件丢失返回 null 不崩。

## 七、已知限制

1. **没做真正的外发**：备份只能复制到剪贴板。数据量大（几千条）时，微信剪贴板可能截断，建议每月导一次 CSV 存到电脑。
2. **备份不含照片文件**：剪贴板 JSON 装不下二进制，备份里只有照片文件名。换机恢复后记录能回来，但照片文件不在，缩略图位置显示「照片文件已丢失」——记录本身不丢，凭证图要自己在换机前另存。
3. **单价记忆按款号，不按码**：同一个款 S 码和 XL 码单价不同时，需要手动改一次。
4. **没有"扎号必填"校验**：整款包干不按扎的场景要允许留空。
5. **改码/改价不会回溯历史**：改的是当前这一笔，历史记录保持原样（这是刻意的）。
6. **只适配竖屏手机**：平板/横屏没专门排版。
7. **没有 OCR**：菲票靠拍 + 放大核对，不识别手写数字，原因见五·补三。

## 七·补：开发中踩到的坑（都记下来，省得再踩）

| 现象 | 真因 | 怎么改的 |
|---|---|---|
| 卡片里的点击没有水波纹；debug 下直接抛断言 `ListTile background color or ink splashes may be invisible` | 水波纹必须画在最近的 `Material` 上，而卡片背景是 `Container(BoxDecoration)` / 玻璃用的 `DecoratedBox`，把它盖住了 | 面板里垫一层 `Material(type: MaterialType.transparency)`，放在渐变之上、内容之下。**换皮时这个坑又踩了一次**——玻璃面板不再是 Material，`mine_page` 的三个 ListTile 立刻抛断言，是 UI 冒烟测试抓到的 |
| 数据层测试里金额越积越多（期望 1000，实际 54680） | sqflite 按**路径**缓存已打开的库，`:memory:` 也是同一个路径，第二个用例拿到上一个用例的库 | 测试里 `OpenDatabaseOptions(singleInstance: false)` |
| UI 测试卡住不结束 | ① 录入页输入框自动聚焦，光标闪烁不断调度新帧，`pumpAndSettle()` 永远等不到空闲；② 组件测试跑在假时钟里，SQLite 是真实异步 I/O，开库那一步不会推进 | 放弃 `pumpAndSettle`，改固定帧 `pump()`；开库/写库放进 `tester.runAsync()` |
| 测试跑完报 `A Timer is still pending even after the widget tree was disposed` | sqflite 每次查询都会挂一个 10 秒事务超时定时器；假时钟下查询永远不完成，定时器就一直挂着 | 每推一帧后 `runAsync(() => Future.delayed(120ms))` 把真实 I/O 排干净，定时器随查询完成取消。见 `test/ui_smoke_test.dart` 的 `settle()` |
| 测 push 进来的页面：`pump(400ms)` 后点「更多码」没反应，只打印一条 warning | 路由转场**不是一次 `pump(duration)` 能推完的**——实测页面可能还没入树；补一帧后出现了，却还挂在屏幕右侧约 200px 的半路。而 `tester.tap` 点到屏幕外的部件**只打印 warning、不抛异常**（静默 miss），setState 从未执行，断言看起来像"功能坏了" | 循环推帧，直到目标部件位置收敛（连续两帧坐标不变）再操作，见 `pumpUntilStill()`。**别信单次长 pump**：推 400ms 和推 4×100ms 的效果不一样 |
| 断言 `find.text` 报二义（同时匹配 chip 和弹窗输入框） | 弹窗收回有转场动画，它的输入框里也是同一串文字，没收完就在树里 | 先等弹窗消失（`pumpUntilGone()`）再断言 |

这六条合起来说明一件事：**UI 测试在这类"真数据库 + 自绘皮肤"的项目里只适合做冒烟，不适合做流程**。用真实本地库去驱动组件测试，会和测试框架的假时钟一直打架；要做全流程测试，正解是先给数据层抽一个接口 + 内存假实现（Fake），再让页面依赖接口。那是另一轮重构，v1.1 不值得为它付代价。所以取舍是：**算钱的部分自动化测死，点按的流程人手过一遍，界面的可靠性靠冒烟兜住**。

## 八、外观系统：两套皮肤（v1.2）

v1.1 把桌面项目**爪 Pro** 的视觉语言整套搬到了手机上；v1.2 保留它，同时把 v1.0 的原样也留了回来，**默认回到经典**。

### 8.1 为什么留两套

v1.1 真机截图证明了一件事：**同一套色值，换到手机竖屏比例就崩**。爪 Pro 是横向宽屏，渐变最亮的粉紫段只占一小块；手机竖屏上这段亮色铺满整个表单区，而页面里有一批文字**不在玻璃面板上、直接压在背景上**（"件数""单价"标签、输入框提示、工序/备注），那些字当时用的是 `#8A76B0` 灰紫，落到亮紫底上对比度只有 1.2:1——人眼等于看不见。

处理办法不是继续硬调色（调完还有下一处），而是**把选择权交给使用者**：

| | 经典皮肤（默认） | 全息皮肤 |
|---|---|---|
| 卡片 | 纯白 / 纯深色实底 | 半透明玻璃 + 模糊 |
| 背景 | 单色 `#F4F6F5` / `#0F1413` | 六层绘制的渐变 |
| 按钮 | Material 原生扁平按钮 | 宝石 / 玻璃 / 描边 / 胶囊 |
| 主色 | 深青绿 `#0E7A63` | 紫 `#9773D2` + 薄荷绿金额 |
| 适合 | 车间强光下看，字最清楚 | 夜里看，质感好 |
| 设置项 | 明暗三选（跟随系统 / 浅 / 深） | 背景 × 玻璃厚度 × 按钮形态 |

**默认给经典**：这本账的第一要求是「看得清」，不是好看。

### 8.2 设置的层次（决定谁能调出什么）

```
皮肤（经典 / 全息）           ← 第一层，先定设计语言
├─ 经典 → 明暗（跟随系统 / 浅色 / 深色）
└─ 全息 → 背景三选 × 玻璃厚度 60~100% × 按钮四形态
```

不做成六个开关平铺，是因为**平铺必然出现自相矛盾的组合**（比如深色文字配深底）。分层之后，每一层里的选项都保证互相兼容。

存在 `settings` 表：`skin` / `mode` / `bg` / `glass` / `btn`。

### 8.3 经典皮肤（`ui/tokens.dart` 里的 `class Ck`）

色值**不是重新配的，是从 v1.0 的 `theme.dart` 原文取回来的**，只有一处改动：

| 用途 | 色值 | 说明 |
|---|---|---|
| 主色 | `#0E7A63` | 深青绿。不用红色的理由：红色在记账语境里等于"亏损"，而这本账是"我挣了多少" |
| 加班/提醒 | `#C2760A` | 琥珀，只用于"需要你看一眼"，不做装饰 |
| 页面底 / 卡片 | `#F4F6F5` / `#FFFFFF` | |
| 深色主题底/卡 | `#0F1413` / `#1A211F` | |
| 文字三级（浅） | `#16201D` / `#3C4A46` / `#5F6B67` | 三级是 `#5F6B67` 而不是 v1.0 的 `#7B8783`——后者在白底只有 3.9:1，偏低 |
| 文字三级（深） | `#FFFFFF` / `#C3CCC9` / `#96A29E` | |

### 8.4 全息皮肤（`class Tok`）

**为什么色值和爪 Pro 原值不一样**：原值是为宽屏调的，手机竖屏上必须压暗 / 提亮，否则就是上面那 1.2:1 的问题。

| 用途 | v1.1 原值 | v1.2 现值 | 为什么改 |
|---|---|---|---|
| 暮光紫第 4 段 | `#C08BB8` | `#7E5786` | 原值是全条渐变最亮的一段，竖屏上铺满表单区 |
| 次要文字 | `#BDA9DC` | `#CBB8E6` | 略提亮 |
| 三级文字 | `#8A76B0` | `#B3A2CE` | **原值只有 1.2:1，等于没有** |
| 内槽填充 | `rgba(0,0,0,.24)` | `rgba(0,0,0,.45)` | 原来在亮底上看不出边界 |
| 宝石顶面 | `#D9C2F0` | `#C9AEEA` | 顶面太浅导致整个按钮发白发灰——这是"土"的主因 |

**一条硬规矩**：紫底上的高光**不能用白色**。白高光在紫底上会发灰发蓝，看起来像塑料；必须用粉紫 `#D9C2F0` 才像晶体透光。这条是爪 Pro 用四轮改色换来的。

### 8.5 背景是画出来的，不是一张图

`ui/background.dart` 的 `LayeredBackground` 按固定顺序叠六层：

```
六段竖向渐变 → 32px 网格线 → 3px 扫描线 → 三团极光(径向) → 四角压暗 → 上下压暗
```

- 用 `CustomPainter` 画，不是贴图：换配色只改令牌，不用重新出图
- 外面套 `RepaintBoundary`：这层几乎不变，不该跟着列表滚动重画
- 挂在 `MaterialApp.builder` 里、**Navigator 下面**，`Scaffold` 背景设透明。这样顶栏/滚动内容/底栏压在同一张渐变上，玻璃才有东西可糊

### 8.6 玻璃的配方

单色半透明看起来像磨砂塑料。真正像玻璃要三件套：

1. **三段渐变填充**：上 78% → 中 86% → 下 90% 不透明（越往下越实，像有厚度）
2. **顶边受光高光线**：1px，两端透明、中间粉紫，只画左右各留一个圆角宽度
3. **斜向 sheen**：122° 方向的极淡反光，模拟镜面

外面再加 `BackdropFilter(blur)`。**CSS 的 `blur: 18px` 约等于 Flutter 的 `sigma: 9`**——CSS 写的是模糊直径，Flutter 要的是标准差，直接抄 18 会糊成一团。

纸白主题不用暗玻璃，改用白玻璃 + 深色描边，否则在浅底上完全没有"面"的感觉。

### 8.7 四种按钮形态

| 形态 | 填充 | 用在 |
|---|---|---|
| 宝石 gem | 四段渐变 `#C9AEEA→#8A5BC9→#522189→#2A0C55` + 外发光 | 默认，主操作（保存、记一笔） |
| 胶囊 pill | 同宝石，圆角 999 | 觉得直角太硬的人 |
| 玻璃 glass | 半透明紫渐变 + 亮描边 | 想要更轻的主操作 |
| 描边 ghost | 无填充，只描边 | 想要最轻的主操作 |

危险操作（停止/删除）**不受形态影响**，永远走语义红 `dangerFill`——皮肤可以换，语义不能换。

### 8.8 取色只有一个入口：`Pal`

`ui/pal.dart` 是页面里**唯一**的取色入口。原因很实际：一段文字该什么颜色，取决于「皮肤 × 明暗 × 它在不在玻璃面板上」三个维度，页面里散着写必然失控——v1.1「看不清字」就是这么来的。

```dart
Pal.hi(context)      // 主文字
Pal.mid(context)     // 次文字
Pal.dim(context)     // 三级文字
Pal.accent(context)  // 强调
Pal.money(context)   // 金额（正向色）
Pal.card(context)    // 卡片底色
```

页面里**不许**再出现 `Tok.txDimOf(appState.bg)` 或任何字面色值。

### 8.9 对比度是被测试钉住的

`test/contrast_test.dart` 把可读性变成**可计算的断言**（WCAG 2.1 阈值：正文 4.5:1 / 次要 3.0:1）：

- 经典皮肤：明暗两套 × 主/次/三级文字，各对其真实底色（含页面底色）
- 全息皮肤：**用渐变里最亮的一段 + 压暗层**当最坏情况，检查压在背景上的字
- 全息皮肤：字在玻璃面板里时，用「玻璃填充叠在亮背景上」的合成色当底
- 宝石按钮四段渐变逐段检查白字对比度
- 输入框内槽里的提示文字

现在共 **56 个用例**（金额 9 + 数据层 10 + 对比度 24 + 码数 9 + UI 冒烟 4）。改任何颜色，测试会直接告诉你哪一处的对比度掉了。
